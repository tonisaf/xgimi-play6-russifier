# Recovery и fastbootd: живой тест 8 октября 2026

**Проверка 12 октября без USB:** [VERIFY-2026-10-12.md](VERIFY-2026-10-12.md). Размеры и SHA256 локальных boot/recovery/super совпали с заново прочитанными действующими разделами. Автономный вход и восстановительная запись по-прежнему не проверены.

Проверенная прошивка XGIMI Play 6 v1.7.116. Системные APK, boot/recovery/super не записывались и не стирались.

## Подтверждённые результаты

- adb reboot recovery из обычного Android загрузил recovery. USB-ADB сразу появился в состоянии recovery на сервере 5038; ручное переключение software_id не понадобилось. Проверены shell, свойства и список разделов.
- В recovery software_id=1, UDC configured; Android 11, ожидаемая v1.7.116. Сетевой транспорт offline. Shell uid=2000, ro.debuggable=0, adb root отказал: adbd cannot run as root in production builds. Super block device root-only 0600. Прямое восстановление через dd из shell не подтверждено.
- adb reboot fastboot загрузил fastbootd; fastboot getvar is-userspace=yes, unlocked=yes, secure=yes. Размер super 0xE0000000 (3758096384), boot/recovery по 0x4B00000 (78643200), совпадают с резервными копиями. is-logical:system=yes и is-logical:vendor=yes.
- partition-type:super вернул FAILED (remote: Fastboot HAL not found), несмотря на код завершения клиента 0. Проверять нужно текст ответа, а не только exit code.
- Fastboot flash/erase/fetch не выполнялись. unlocked=yes и видимость разделов не являются живым доказательством возможности восстановления.

## Возврат

fastboot reboot ответил OKAY. Пользователь подтвердил: после команды проектор выключился. Сетевой ADB, USB и fastboot пропали. Автоматический возврат в Android не состоялся; запрошено включение обычной кнопкой питания. После ручного включения загрузка подтверждена сетевым ADB: sys.boot_completed=1, bootanim=stopped, исходная прошивка v1.7.116, software_id=0 (host). Это наблюдаемое поведение данной модели, причина выключения пока не установлена.

## Ограничения аварийного восстановления

Переход в recovery и fastbootd подтверждён программными командами при рабочем Android/recovery. Вход аппаратными кнопками при неисправном system ещё не проверен. Резервные копии существуют; применение их через fastbootd не тестировалось. Постоянная замена APK пока не выполнена.

Локальные диагностические логи recovery-readonly.txt, adb-root.txt, recovery-permissions.txt и fastboot-readonly.txt исключены из Git; содержат сведения об устройстве. Отчёт публикуется без серийного номера и полных дампов.

## Итог возврата

Ручное включение штатной кнопкой питания вернуло рабочий Android и сетевой ADB. Подтверждён маршрут: рабочий Android → recovery по USB → fastbootd по USB → команда reboot выключает проектор → ручное включение → Android. Нельзя описывать последнюю команду как автоматическую перезагрузку в рабочий Android.

Для безопасной постоянной замены ещё необходимы аппаратный вход в recovery при недоступном Android и подтверждённый способ записи резервной копии. Ни аварийный вход кнопками, ни восстановление раздела пока не проверены.

## Подготовка аппаратного входа

В MBOOT найдены отдельные обозначения RECOVERYWIPEDATA_KEY, RECOVERYWIPECACHE_KEY, FASTBOOT_KEY и BRICK_TERMINATOR_RECOVERY_KEY. Наличие строк не доказывает, что соответствующие функции включены или доступны штатным пультом данной модели.

Прочитана реальная конфигурация G0058: /mnt/vendor/xgimiconfig/G0058/keypad/keypad.ini, type=10 (MCU_ONLY_KEY), enter_update_time=4000 мс. Активный dataIndex_1.ini указывает /vendor/cusdata/bsp/board/BD_MT5889_H2V1-B4-S/ir_config.ini. В секциях Mboot есть отдельные recovery и wipe-коды NEC header 0x21DE; не рекомендованы как обычные кнопки пульта, соответствие пульту не проверено. Кнопочный режим обновления нельзя заранее приравнивать к Android recovery.

Запрошен ограниченный аппаратный тест: выключенное устройство, питание и USB-кабель к ПК, удержание кнопки корпуса около 5 секунд, без носителя с прошивкой и без выбора пунктов меню. Результат ещё ожидается. Системные разделы не изменены.

PDF инструкции найден в каталоге, но исходное содержимое не прочитано: прямые загрузки вернули HTTP 403; текстовый пересказ стороннего сайта не использован как доказательство. Команда fetch присутствует в помощи установленного fastboot-клиента, но поддержка на Android 11 fastbootd этого проектора не доказана. Наличие клиентской команды не подтверждает поддержку устройством.

## Результат аппаратного удержания кнопки

Пользователь проверил удержание кнопки корпуса из выключенного состояния: появился режим загрузки пакета, затем сообщение о ненайденном пакете и обычный запуск. Возврат Android подтверждён сетевым ADB (sys.boot_completed=1, v1.7.116). Это вход в загрузку OEM-пакета, **не подтверждённый вход в recovery/fastbootd**. Наши raw boot/recovery/super образы не являются OEM-пакетом; скачанный старый зашифрованный BIN не заменяет подготовленный способ восстановления текущей прошивки.

В текущем ir_config.ini присутствуют кандидаты NEC header 0x21DE, RECOVERY_KEY=0x1B и 0x95 в двух профилях. Активность этих профилей в сохранённой таблице загрузчика и соответствие штатному пульту не подтверждены. Строки парсера MBOOT содержат отдельные FASTBOOT_KEY и BRICK_TERMINATOR_RECOVERY_KEY, но в просмотренном INI их значения не заданы. Wipe-коды не испытывались. У пользователя уточнено наличие ИК-передатчика; произвольные кнопочные комбинации не подбирались.

## Уточнение Fastboot HAL

В исходниках AOSP Android 11 GetPartitionType возвращает Fastboot HAL not found, когда отсутствует fastboot HAL для запроса типа файловой системы. FlashHandler проверяет статус блокировки и вызывает отдельный Flash → OpenPartition → запись. Поэтому наблюдавшаяся ошибка getvar partition-type:super сама по себе не доказывает запрет flash. Это вывод по эталонным исходникам, не доказательство идентичности сборки XGIMI или успешного восстановления. Реальная запись разделов не выполнена.

## Проверка имеющегося ИК-пульта

У пользователя есть штатные Bluetooth- и ИК-пульты. В работающем Android прочитаны события MStar Smart TV IR Receiver (/dev/input/event1), без изменения параметров драйвера. В течение 45 секунд получены MSC_SCAN 0021de0e (DOWN), 0021de17 (VOLUMEDOWN), 0021de42 (BACK; три нажатия). Наблюдаемый адрес 21DE совпадает с конфигурацией. Исходный ИК-лог не содержит серийных номеров, но остаётся локальным диагностическим артефактом.

Пользователь перечислил ИК-кнопки: стрелки, OK, громкость, Назад. По совпадающей карте KIR_ChinaMobile ожидаются UP=0B, DOWN=0E, LEFT=10, RIGHT=11, OK=CE, VOLUP=18, VOLDOWN=17, BACK=42. Из них фактически сняты DOWN/VOLDOWN/BACK; остальные значения взяты из конфигурации. Кандидаты RECOVERY_KEY 1B/95 отсутствуют среди этой группы назначений. Поэтому обычный ИК-пульт, вероятно, не отправляет нужную recovery-команду. Скрытые комбинации не проверены; их наличие не предполагается.

Следующий технический вариант: управляемый ИК-передатчик для конкретного кандидата NEC 21DE/1B или 21DE/95, либо подтверждённая сервисная процедура производителя. Даже произвольная отправка этих кандидатов не гарантирует вход: активность сохранённой bootcheck-таблицы ещё не проверена. Известные wipe-команды не отправляются.

До подтверждённого автономного входа и способа применения копии реальные system/vendor APK не заменены.
